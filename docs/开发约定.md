# 开发约定

> 本仓已有的约定大多散落在各处注释里，新人（或三个月后的自己）加代码时容易走样。
> 这里把它们集中写下来，**新增代码前先扫一眼**。

---

## 1. 分层与依赖方向

```
api  →  services  →  agent  →  repositories  →  models / entities
                                  ↑
                              clients（连接管理）
```

**依赖只能自上而下**，不能反向。具体地：

- `repositories` **不允许** import `agent` 或 `services`
- `entities` 是纯 dataclass，**不依赖任何内部模块**（所以它最适合做包级导出）
- `clients` 只管连接生命周期，不含业务逻辑

判断你的新模块该放哪层，先问："它依赖谁、谁依赖它"。如果发现要反向 import，多半是分层错了。

## 2. 错误处理

这是全仓最需要统一、也最容易写歪的一处。**按层次区分**：

### 2.1 Agent 节点：发 error 事件 → raise

```python
async def some_node(state: DataAgentState, runtime: Runtime[DataAgentContext]) -> dict:
    writer = runtime.stream_writer
    writer({"type": EventType.PROGRESS, "step": "某步骤", "status": RunStatus.RUNNING})
    try:
        result = await do_something()
        writer({"type": EventType.PROGRESS, "step": "某步骤", "status": RunStatus.SUCCESS})
        return {"some_field": result}
    except Exception as e:
        writer({"type": EventType.PROGRESS, "step": "某步骤", "status": RunStatus.ERROR})
        logger.error(f"某步骤失败:{e}")
        raise                      # ← 关键：必须抛出去
    raise
```

**两个要点**：

1. **必须 `raise`**。吞掉异常会让 LangGraph 以为这一步成功了，带着不完整的数据继续往下跑，
   最终表现成"生成的 SQL 莫名其妙"——排查成本极高。
2. **必须先发 `status: error` 的 progress 事件**，再 raise。前端靠这个事件把该步骤标红；
   只 raise 不发事件的话，用户看到的是一直转圈的步骤，不知道哪里断了。

### 2.2 `validate_sql` 是刻意的例外：返回 `{"error": ...}` 而不抛

```python
except Exception as e:
    writer({"type": EventType.PROGRESS, "step": "验证SQL", "status": RunStatus.ERROR})
    logger.error(f"SQL验证失败: {sql}")
    return {"error": str(e)}       # ← 不 raise
```

**为什么它不一样**：SQL 校验失败是它**要表达的业务结果**，不是异常。图靠 `state["error"]`
是否为 `None` 来决定走 `execute_sql` 还是 `correct_sql` 分支。

区分原则：**"这个失败是调用方需要知道并据此决策的信息" → 返回值；
"这个失败意味着当前流程没法继续" → raise。**

### 2.3 Repository 层：不 catch，直接抛给节点

```python
async def execute_sql(self, sql: str) -> list[dict]:
    result = await self.session.execute(text(sql))
    return [dict(row) for row in result.mappings().fetchall()]
    # 没有 try/except —— 数据库报错原样抛给调用方
```

Repository 不该决定"失败了怎么办"——那是节点的职责。在仓库层吞异常会让节点拿到
一个看似正常的空结果。`server/repositories/` 下**没有任何一处 try/except**，这是有意的。

### 2.4 可降级的上游依赖：记 WARNING，不中断

当某个输入只是"锦上添花"、缺了也能继续时，单独 try/except 降级：

```python
# server/agent/nodes/add_extra_context.py
try:
    data_range = await dw_mysql_repository.get_data_date_range()
except Exception as e:
    logger.warning(f"获取数据时间范围失败，降级为空范围: {e}")
    data_range = {"start": None, "end": None}     # 不让整条问句失败
```

判断标准：**没有这个信息，SQL 还能不能生成？** 能 → 降级；不能 → raise。

### 2.5 评测：单条失败不中断整轮

评测一轮要跑几十分钟，**任何一个用例的异常都不该让整轮白跑**：

- 单条用例异常 → 用 `_error_row()` 生成占位行，保证 CSV 字段对齐、继续下一条
- 裁判调用失败 → 只在该条记录失败原因，`execution_accuracy` 照常算

```python
# eval/run_ragas_eval.py
try:
    row = await evaluate_case(...)
except Exception as e:
    row = _error_row(case, e)      # 占位，不中断
```

## 3. 事件协议与状态字符串

**跨进程边界的字符串必须用枚举**（`server/agent/events.py`）：

| 枚举 | 取值 | 用途 |
|---|---|---|
| `EventType` | `PROGRESS` / `RESULT` / `ERROR` | SSE 事件类型 |
| `RunStatus` | `RUNNING` / `SUCCESS` / `ERROR` | 节点执行状态 |
| `ExecAccuracy` | `CORRECT` / `INCORRECT` / `EMPTY_BOTH` | 评测执行准确性结论 |

```python
# ✅ 正确
writer({"type": EventType.PROGRESS, "step": "生成SQL", "status": RunStatus.RUNNING})

# ❌ 不要
writer({"type": "progress", "step": "生成SQL", "status": "running"})
```

**为什么用 `StrEnum`**：这些值要 `json.dumps` 后经 SSE 发给前端，前端按字符串比较。
`StrEnum` 的成员本身就是 `str`，序列化出来仍是 `"progress"`，因此线协议零改动。
（普通 `Enum` 会序列化成 `"EventType.PROGRESS"`，那是破坏性变更。）

**规则**：凡是要写进 SSE、写进 CSV、被前端或外部脚本读取的字符串，一律用枚举；
纯模块内部的一次性字符串不必。

## 4. 包级导出（`__init__.py`）

`__init__.py` 里做 re-export，让调用方少写几层路径：

```python
from server.conf import app_config
from server.entities import ColumnInfo
from server.repositories import DWMySQLRepository
from server.agent import DataAgentState
```

**但有一条硬规则：不要导出重依赖。**

> ⚠️ `server/agent/__init__.py` **刻意不导出 `graph`**。
> `graph.py` 会连带加载 13 个节点、LLM、仓储、prompt 加载器。一旦写进包初始化，
> 任何 `from server.agent.state import ...` 都会先把整条流水线加载一遍，而且大幅提高
> 循环导入概率（节点反过来导入本包时会撞上"包尚未初始化完"）。
> 正确写法是让调用方显式 `from server.agent.graph import graph`，
> 把重依赖暴露在调用点而不是藏进包里。

**能放进 `__init__.py` 的**：叶子模块（无内部依赖，如 `entities`）、
或只依赖同包的模块（如 `conf`）。**放不进的**：会拉进大量传递依赖的模块。

## 5. 类型标注

- **函数参数与返回值都要标**。当前 `server/` 覆盖率约 94%（99 个函数里 93 个）。
- 同一个类里**风格必须一致**——`dw_mysql_repository.py` 曾经 6 个方法两种风格，
  读者会以为"没标是有意的"。

```python
async def get_db_info(self) -> dict: ...
async def execute_sql(self, sql: str) -> list[dict]: ...
async def validate_sql(self, sql: str) -> None: ...
```

节点函数统一标 `-> dict`（返回 state 的部分更新）。

## 6. 代码风格：ruff

```bash
uv run ruff check --fix      # 自动修可修的
uv run ruff format           # 统一排版
```

配置在 `pyproject.toml` 的 `[tool.ruff]`。要点：

- **行宽 120** 而不是默认 88：本仓注释以中文为主，ruff 按**字符数**计长，
  中文一句 40 字就接近 88 了，用默认值会产生大量无意义告警
- 启用 `E/W/F/I/UP`；**暂不启用 `B`(bugbear) / `SIM`(simplify)**，
  待风格收敛后单独评估

> `ruff format` 会重排全仓（实测约 2800 行）。**建议单独一次提交做这件事**，
> 不要和功能改动混在一起——否则 diff 里分不清哪些是逻辑变更。

## 7. 日志

- 统一用 `from server.core import logger`（loguru），**不要用标准库 logging**
- 日志路径按**项目根**解析，不随当前工作目录漂移（`server/core/log.py` 的 `PROJECT_ROOT`）。
  历史上因为用相对路径，仓库里散落过 5 个 `logs/` 目录
- 节点级 INFO 日志量大（一轮评测上千行），跑评测时用 `--verbose-logs` 才打到控制台，
  默认写入 `logs/eval_*.log`

---

## 8. 配置

- 可调参数放 `conf/app_config.yaml`（**不入库**），模板是 `app_config.example.yaml`
- 元知识的表/字段/指标定义放 `conf/meta_config.yaml`（入库）

> ⚠️ **改过 `meta_config.yaml` 必须重建元知识库**——字段描述参与 embedding，
> 不重建则召回仍用旧描述：
> ```bash
> uv run python -m scripts.rebuild_meta -c conf/meta_config.yaml
> uv run python -m scripts.check_meta
> ```

---

## 9. 测试

| 层 | 位置 | 要求 |
|---|---|---|
| 单元测试 | `tests/unit/` | **不得依赖中间件**；能纯逻辑验证的一律放这里 |
| 集成测试 | `tests/integration/` | 需要中间件，默认跳过，`RUN_INTEGRATION=1` 开启 |
| 评测 | `eval/` | 不是测试，是质量度量——**不要塞进 CI**（几十分钟且有噪声） |

新加一层就建 `tests/unit/test_<层>_layer.py`，命名与现有文件保持一致。

**可测试性驱动的拆分**：把纯逻辑从 I/O 里拆出来，是为了能离线单测。例如
`scripts/dataset_checks.py`（纯规则）与 `scripts/validate_dataset.py`（连库编排）、
`eval/equivalence.py`（纯判定）与 `eval/run_ragas_eval.py`（跑系统）。
新写工具时优先考虑这个拆分。
