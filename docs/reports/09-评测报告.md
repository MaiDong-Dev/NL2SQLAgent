## 1. 一句话结论

把评测集从 33 条扩充到 63 条后，系统**执行准确率 98.41%（62/63）**、SQL 语义等价率 0.857，
但**字段召回精确率从 0.736 回落到 0.523**——这是我一处降噪改动带来的副作用，原因已定位，方案已给出（见第 8 节）。

| 阶段 | 用例数 | linking_precision | linking_recall | sql_equivalence | execution_accuracy |
|---|---|---|---|---|---|
| 基线（原始 33 条） | 33 | 0.489 | 0.802 | 0.939 | **100%**（33/33） |
| 第一轮（扩充后 63 条） | 63 | 0.736 | 0.826 | 0.730 | 84.13%（53/63） |
| 第二轮（修复后 63 条） | 63 | **0.523** | 0.844 | 0.857 | **98.41%**（62/63） |

怎么读这张表：

- 第一轮执行准确率从 100% 掉到 84%，**不是系统退化**，是新加的 30 条题目刻意覆盖了更难的模式
  （条件聚合、HAVING 过滤、金额分桶、占比子查询、时间差值），打到了真实能力边界。
- 第二轮执行准确率回到 98.41%，一部分来自系统修复，一部分来自我修正了自己出的歧义题（第 6.3 节）。
- 精确率回落 0.213 是真实代价，不能装看不见，第 8 节专门分析。
- 表中的 `sql_equivalence` 是 **ragas（DeepSeek 裁判）** 口径。7.3 节用 Jev 决策模型对同一批 63 条
  重做了一次判定，等价率 **0.968**（F1 0.984 vs ragas 的 0.931），成本 $0.0034——裁判环节可以换得更便宜也更准。

## 3. 评测集：从 33 条扩充到 63 条

### 3.1 出题前先摸数据（这一步省不掉）

新增题目之前，我先探查了 `dw` 库的真实数据分布，因为**凭印象出题会造出返回空结果的废题**。两个关键发现：

1. **数据仓库只有 2025 年 Q1（1~3 月）共 115 笔订单**，没有 2024 年、没有 Q2~Q4。
   这直接否掉了跨年对比、同比环比、分季度趋势等一批题目；所有新题的时间条件都限制在 2025 年 1~3 月。
2. 维度取值的真实边界：`member_level`=黄金/白银/青铜/铂金，`category`=手机数码/家用电器/鞋靴/服饰/食品饮料/休闲零食，
   `province`=上海市/北京市/四川省/广东省/浙江省/湖北省，`country` 只有"中国"（无区分度，不能用来分组）。

顺带发现**之前埋的一个坑**：`scripts/smoke_heldout.py` 里的冒烟问句包含"2024年华东大区每月订单量""铂金会员在第四季度"，
都在数据范围之外，返回空结果。而我之前报告"8 条全部通过"时只看了没报错、没看行数——那个结论是虚的。
已把这两条改成范围内的问法，并给脚本加了两条自动告警：结果为空、对 `date_id` 做算术/字符串处理。

### 3.2 入库前的三重校验

每条新用例在写进 `dataset.jsonl` 之前都要过三道关：

1. **参考 SQL 真实执行且结果非空**——避免造出语法对但查不到数据的题；
2. **`reference_columns` 必须在 `meta.column_info` 中存在**——避免标注了系统永远召不回的字段，冤枉系统；
3. **问句不与现有题目重复**。

校验立刻抓到一条：「服饰品类中耐克品牌的销售额是多少」返回 NULL——因为**耐克属于鞋靴，不属于服饰**。改成鞋靴才通过。

### 3.3 题型分布

原有 33 条保留不动，新增 30 条刻意补了原集没覆盖的模式：

| 新增题型 | 示例 |
|---|---|
| 条件聚合（CASE WHEN / 差值） | 「2025年1月与3月的销售额相差多少」 |
| HAVING 过滤 | 「销售额超过30000的省份及其销售额是多少」 |
| 金额过滤后计数 | 「订单金额超过5000元的订单有多少笔」 |
| 占比子查询 | 「手机数码品类的销售额占总销售额的百分比是多少（保留两位小数）」 |
| 排除条件 + 汇总 | 「除手机数码外其他品类的销售额是多少」 |
| 时间 + 维度 + TopN 复合 | 「2025年3月销量最高的商品是哪个」 |
| 多指标并列 | 「订单总数、总销售额、平均订单金额分别是多少」 |
| 按天粒度 | 「2025年1月每天的订单量是多少」 |
| 多条件交叉 | 「2025年2月华东大区女性会员的订单量是多少」 |
| 维度+指标分组排序 | 「各品牌在各地区的销售额排名」 |

格式（每行一条）：

```json
{"query": "问句", "reference_sql": "标准 SQL", "reference_columns": ["fact_order.order_amount", "..."]}
```

## 4. 评测指标体系

评测分三层，对应系统的三段流水线。**为什么不全用 LLM 打分**：LLM 裁判会飘，而召回层和执行层是可以确定性判定的，
所以只在真正需要语义理解的地方（SQL 等价性）才用 LLM。

### 4.1 第一层：Schema Linking 质量（不用 LLM）

把「字段 ID」当作文档 ID（如 `fact_order.order_amount`），与标注的标准字段集合比对：

- `linking_precision` = 召回字段中属于标注集合的比例（**召得准不准**，噪音多就低）
- `linking_recall` = 标注集合中被召回的比例（**召得全不全**，漏了就 SQL 必错）

用 Ragas 的 `IDBasedContextPrecision` / `IDBasedContextRecall`。成本为 0、结果确定、可复现。

### 4.2 第二层：SQL 语义等价性（裁判 LLM）

`sql_equivalence`，用 Ragas 的 `SQLSemanticEquivalence`，由裁判 LLM 判断「生成的 SQL」与「标准 SQL」是否语义等价，
同时把 DW 库的建表 DDL 作为上下文传给裁判。

**这里踩过一个坑**：Ragas 自带的 prompt 会把 `region_name AS 大区` 这类别名差异判为不等价，
导致等价率（0.56）远低于执行准确率（0.78），明显失真。我重写了裁判 prompt（`Nl2SqlEquivalencePrompt`），
明确以「同一数据库状态下返回的数据集合是否相同」为唯一标准，并逐条列出哪些差异不影响等价
（别名、列顺序、行顺序、时间口径的不同写法、语法糖）、哪些构成不等价（聚合函数不同、过滤条件缺失或多余、
分组粒度不同、JOIN 不同、实质列数量不同、LIMIT 条数不同）。

第 7.3 节做了一次**裁判替换实验**：用 Jev 决策模型（不生成文本的 System One 模型）跑同一批 63 条，
与本节的 DeepSeek 裁判对照——判定质量更高（F1 0.984 vs 0.931），成本约 $0.0034 / 63 条。

### 4.3 第三层：执行准确性（主指标）

`execution_accuracy`，自定义离散指标，**真正执行两条 SQL 比对结果集**，这是 NL2SQL 领域公认的主指标。

判定规则：

- 生成 SQL 执行失败 → `incorrect`
- 两边都返回 0 行 → `empty_both`（空集 == 空集不能证明等价，可能是过滤条件写错，故不计通过，需人工复核）
- 结果集一致（忽略行序、浮点数取 6 位精度）→ `correct`
- 列名不同但数据一致 → `correct`（别名不该判错）

## 5. 被测系统的处理链路

系统是一条 LangGraph 流水线（`server/agent/graph.py`），评测时直接 `graph.astream()` 跑完整条链路，
同时用 `stream_mode=["custom", "updates"]` 抓两样东西：最终执行结果（result/error）和中间状态（召回字段、生成的 SQL）。

```
START
  ↓
extract_keywords          jieba 分词 + 词性过滤（不用 LLM）
  ↓
┌─────────────────┬─────────────────┐
recall_column     recall_value      recall_metric     三路并行召回
（字段向量召回）   （取值 ES 召回）  （指标向量召回）
└─────────────────┴─────────────────┘
  ↓
merge_retrieved_info      合并三路结果、补全元数据
  ↓
┌─────────────────┐
filter_table      filter_metric                       LLM 裁剪表/字段、裁剪指标
└─────────────────┘
  ↓
enrich_metric_columns     按保留下来的指标补全其关联字段
  ↓
add_extra_context         补充当前日期、数据库版本
  ↓
generate_sql              LLM 生成 SQL
  ↓
validate_sql              EXPLAIN 验证（不实际执行，零副作用）
  ↓
error? ── 有 ──→ correct_sql（LLM 修正）──┐
        └─ 无 ───────────────────────────┤
                                          ↓
                                     execute_sql → END
```

## 6. LLM 是怎么用的

### 6.1 业务链路：6 个节点调用 LLM

全部通过 `server/agent/llm.py` 的全局单例调用，`temperature=0`，
用 LangChain 的 `prompt | llm | output_parser` 链，输出统一解析为 JSON。

| 节点 | 干什么 | 输入 | 输出格式 | Prompt 文件 |
|---|---|---|---|---|
| `recall_column` | 推断回答该问题**必需的字段名**，作为向量检索的检索词（弥补 jieba 不懂业务语义） | 用户问句 | JSON 数组：`["销售额","订单日期","商品品类"]` | `extend_keywords_for_column_recall.prompt` |
| `recall_value` | 推断可能出现在**字段取值**中的关键词（枚举值、实体名） | 用户问句 | JSON 数组 | `extend_keywords_for_value_recall.prompt` |
| `recall_metric` | 推断**指标意图**并补同义词（"GMV"→"成交额"） | 用户问句 | JSON 数组 | `extend_keywords_for_metric_recall.prompt` |
| `filter_table` | 扮演查询规划专家，从候选 schema 里裁掉无关表和字段，减少 prompt 噪音 | 问句 + 候选表信息（YAML） | JSON 对象：`{"fact_order":["order_amount"],"dim_date":["year","month"]}` | `filter_table_info.prompt` |
| `filter_metric` | 从候选指标里只留下真正需要的（纯列表查询不选指标） | 问句 + 候选指标（YAML） | 筛选后的指标 | `filter_metric_info.prompt` |
| `generate_sql` | 生成最终 SQL | 问句 + 表信息 + 指标定义 + 日期信息 + 数据库版本 | 纯 SQL 文本 | `generate_sql.prompt` |
| `correct_sql` | SQL 验证失败时，依据报错做**最小必要修改** | 问句 + 上下文 + 报错信息 | 修正后的 SQL | `correct_sql.prompt` |

`extract_keywords` **刻意不用 LLM**：jieba 分词 + 词性过滤足够，省一次调用、省延迟。

`generate_sql` 的 prompt 里有两条硬约束，是之前踩坑后加进去的：

- **时间口径必须走时间维度表**：涉及年/季度/月/日必须 JOIN `dim_date` 并用其粒度字段，
  严禁对事实表 `date_id` 做算术运算（`DIV`/`MOD`）或字符串函数（`DATE_FORMAT`/`SUBSTR`）提取时间；
- **SELECT 只输出必需的列**：排名语义一律用 `ORDER BY`（必要时 + `LIMIT`）表达，禁止 `RANK()` 等窗口函数排序列；
  用户问"哪个"只输出维度列，问"排名/前N名/有哪些"才输出维度列 + 度量列。

### 6.2 Embedding 怎么用

`BAAI/bge-large-zh-v1.5`（1024 维）。**每个字段在库里有 `name`/`description`/`alias` 三条向量**，
所以检索时按 `column_search_limit=15` 过采样，再按字段去重（实测约覆盖 5~8 个不同字段）。

### 6.3 评测裁判 LLM

用 `AsyncOpenAI` + Ragas 的 `llm_factory` 构造，模型同样是 `deepseek-v4-flash`，
`max_tokens` 提到 4096（默认 1024 会让结构化输出被截断，抛 `IncompleteOutputException`）。
裁判失败不会中断整轮评测，只在该条记录失败原因。

### 6.4 一次问答的 LLM 调用量

一条问句 = 业务链路 **6~7 次**（三路扩关键词 3 次 + 裁剪 2 次 + 生成 1 次，SQL 验证失败时再加 1 次修正）
+ 评测裁判 **1 次**。跑一轮 63 条约 **440 次** LLM 调用。

## 7. 评测过程

### 7.1 第一轮：扩充后跑全量（63 条）

结果：`precision 0.736 / recall 0.826 / equivalence 0.730 / execution 84.13%（53/63）`。

10 条失败逐条复盘，分成三类：

**① 一条是真回归（我的降噪改动引入的）**

「华为品牌商品的销售数量是多少」系统生成了 `COUNT(order_id)`，而正确答案是 `SUM(order_quantity)`。
查召回明细发现：**`order_quantity` 根本没被召回**。

根因是我把向量召回的相对阈值做成了**全句统一**：维度词"华为品牌"相似度 1.000，
而度量词"销售数量"对应的 `order_quantity` 只有约 0.85，被 0.9 的相对阈值整体裁掉了。
维度词和度量词的绝对分数本来就不可比（它们命中问句的不同部分），用同一个阈值必然互相压制。

**② 一处是评测脚本自己的 bug**

MySQL 的 `SUM/COUNT` 聚合返回 `Decimal`，而 `COUNT(...)-COUNT(...)` 这类表达式返回 `int`。
同一个数值 9 会表现成 `Decimal('9')` 和 `9`，字符串化后是 `'9.0'` 与 `'9'`，被判成不一致。
修了 `_canon`，把 `int` 也统一转成 float 再取 6 位小数。

**③ 七条是我自己出题的歧义（这个要认）**

| 问题类型 | 例子 | 怎么改的 |
|---|---|---|
| 行列之争：条件聚合（列式）和 `GROUP BY`（行式）两种答案都对 | 「1月、2月、3月各自的销售额」 | 改成单值输出的问法：「1月与3月的销售额相差多少」 |
| 输出列数量不明确 | 「销售额超过30000的省份有哪些」（只列省份其实也合理） | 问句写清楚：「…省份及其销售额是多少」 |
| 「比例」和参考 SQL 里的「×100 百分比」自相矛盾 | 「…占总销售额的比例是多少」 | 问句明确「百分比（保留两位小数）」 |
| 参考 SQL 有 `ROUND` 但问句没提 | 「平均每笔订单卖出多少件商品」 | 问句补「（保留两位小数）」 |
| 分桶题的区间标签是字符串，系统标签不同就永远对不上 | 「金额低于1000/1000到5000/高于5000分别多少笔」 | 改成单值问法：「订单金额超过5000元的订单有多少笔」 |

**教训**：评测题必须答案唯一。凡是参考 SQL 里的格式化（`ROUND`）、输出列数量、行式还是列式，
都必须在问句里显式约束——否则测的是"猜标准答案"，不是 NL2SQL 能力。

### 7.2 第二轮：修复后重跑（63 条）

改了三件事：召回阈值改成**按关键词独立计算**、评测脚本数值类型归一、7 条歧义题修正。
结果：`precision 0.523 / recall 0.844 / equivalence 0.857 / execution 98.41%（62/63）`。

**只剩 1 条失败**，而且是系统的真实短板，不是标注问题：

> 问：除手机数码外其他品类的销售额是多少
> 系统：`SELECT category, SUM(order_amount) ... WHERE category <> '手机数码' GROUP BY category`（返回 5 行，按品类分组）
> 标准：`SELECT SUM(order_amount) ... WHERE category <> '手机数码'`（返回 1 行，汇总值）

问的是"是多少"（要一个汇总值），系统却按品类拆开了——**排除条件 + 汇总**这种语义它还没学会。

### 7.3 裁判模型对照实验：Jev vs ragas（DeepSeek）

第二轮评测之后补做了一次实验：**裁判环节能不能不用通用聊天模型**。
注意这次实验**没有动业务链路，也没有重跑流水线**——复用第二轮 `results_20260919_171653.csv`
里已有的 `query / reference_sql / predicted_sql`，只换掉"怎么判等价"这一步。

#### 7.3.1 为什么想到用 Jev

`~typesafe/jev-latest` 是 TypeSafe 的 **System One 模型**：它**不生成文本**，
只把一段 state 和一组预先定义好的问题转成带校准概率的类型化答案（是/否、多选一、打分）。
一次请求里所有问题**并行**评估，单价按输入 token 计、输出免费。

SQL 等价性这件事，本质是判断题（"这两条 SQL 查出的数据是不是同一批"），
而不是创作题。用会写字的通用 LLM 去做，等于花钱让它先写两段解释再给结论——
我们真正消费的只有最后那个结论。这就是替换的动机。

#### 7.3.2 接入方式

走 OpenRouter 的决策接口（alpha），不走聊天补全：

```
POST https://openrouter.ai/api/alpha/decisions
Authorization: Bearer $OPENROUTER_API_KEY
```

请求体（`state` 用纯文本拼装：问句 + 标准 SQL + 生成 SQL）：

```json
{
  "model": "~typesafe/jev-latest",
  "state": "用户问句: 各大区的销售总额\n\n标准SQL(reference):\n...\n\n生成SQL(response):\n...",
  "questions": {
    "same_result": {
      "type": "noul",
      "instructions": "在同一份数据库数据上，两条 SQL 返回的数据集合是否相同？",
      "criteria": {
        "true": "查出的是同一批数据，仅别名/列顺序/行顺序不同也算相同",
        "false": "聚合口径、过滤条件、分组粒度、JOIN、LIMIT 任一不同导致数据不同"
      }
    }
  }
}
```

响应（概率直接可用，不用解析文本）：

```json
{"model": "typesafe/jev-1.13-20260917",
 "answers": {"same_result": {"type": "noul", "noul": 0.97}},
 "usage": {"input_tokens": 561, "output_tokens": 39, "cost": 0.000023562}}
```

`criteria` 里写的是**具体情境**（"聚合函数不同""一方有 LIMIT 另一方没有"），
而不是"轻微/严重"这类抽象词——官方明确说抽象档位会把概率摊平。

接入 `run_ragas_eval.py` 后，Jev 与 ragas 拿到**同一份建表 DDL** 作为 schema 上下文，
保证两者对照公平。

#### 7.3.3 实验设计：两种判定口径

每条用例一次请求，state 相同，并行问 7 个问题：

| 问题 | 问什么 |
|---|---|
| `same_result` | **总体**：两条 SQL 返回的数据集合是否相同 |
| `same_tables` / `same_agg` / `same_filter` / `same_group` / `same_limit` / `same_columns` | 6 个原子维度：表与关联键、聚合、过滤条件、分组粒度、LIMIT、SELECT 实质列 |

由此得到两种口径：

- `jev_overall`：直接用总体问题的概率过阈值（0.5）；
- `jev_composite`（Composite scoring）：6 个原子全部为"是"才判等价。

金标用 `execution_accuracy`（真跑库比对结果集），ragas 的 `sql_equivalence` 作为对照。

#### 7.3.4 结果

63 条，以执行结果为金标：

| 判定口径 | acc | precision | recall | F1 | TP | FP | FN | TN |
|---|---|---|---|---|---|---|---|---|
| **Jev 总体判断** | **0.968** | 1.000 | 0.968 | **0.984** | 60 | 0 | 2 | 1 |
| Jev 原子合成 | 0.873 | 1.000 | 0.871 | 0.931 | 54 | 0 | 8 | 1 |
| ragas（DeepSeek） | 0.873 | 1.000 | 0.871 | 0.931 | 54 | 0 | 8 | 1 |

三个口径的 **FP 都是 0**：没有一条"实际不等价"被误判成等价，那条真正失败的用例都被正确判否。

与 ragas 的一致率 90.48%（57/63）。**6 处分歧里 Jev 全对、ragas 全错**——
都是执行结果明明 `correct`、ragas 却判不等价的用例（子查询 vs JOIN、
`DATE_FORMAT(date_id,'%Y-%m')` vs `month` 列这类等价写法）。
换成 Jev 口径，等价率指标从 0.857 提升到 **0.968**。

#### 7.3.5 一个反直觉的发现：原子拆分反而更差

我原本以为按官方推荐的 Composite scoring 拆成 6 个原子判断会更稳，
实测**原子合成与 ragas 分数一模一样（F1 0.931）**，比单点总体判断低了 0.053。

原因是原子问题要求"表与关联键一致""聚合方式一致"，而很多**等价的不同写法**
会被原子判成不一致：

| 用例 | 被判否的原子 | 实际情况 |
|---|---|---|
| 2025年每个月的订单量是多少 | `same_tables` | 一方 JOIN `dim_date` 用 `month` 列，另一方用日期函数，查出的数据相同 |
| 一共有多少笔订单 | `same_agg` | `COUNT(*)` 与 `COUNT(order_id)` 等写法差异 |
| 男女客户分别下了多少单 | `same_filter` | 分组写法不同但筛选出的记录集合相同 |

而总体问题问的是"数据集合是否相同"，天然容忍写法差异——**这正是 4.2 节定的判定口径**。

结论：**判定用单点总体概率，原子问题降级为"失败原因归因"和"低置信度复核触发器"**，
不要拿它当判定口径。这也说明"拆得越细越好"不是普适的，取决于拆解后的子问题
是否和最终口径同向。

#### 7.3.6 成本、延迟与稳定性

| 项 | 数值 |
|---|---|
| 总输入 token | 81,255（63 条） |
| 总花费 | **$0.003413**（$0.000054/条，输出免费） |
| 总耗时 | 12.8s（并发 5；单条直连约 1.5s） |
| 概率分布 | 中位数 0.97，min 0.07，max 0.99 |

**只有 2/63 条落在 [0.4, 0.6] 的纠结区间**——说明概率没有糊在 0.5 附近，
阈值取 0.5 即可，判定结果对阈值不敏感（这点比"调阈值"重要得多，
如果概率都聚在中间，换什么阈值都救不回来）。

#### 7.3.7 边界：这次实验不能推广到业务链路

1. **只验证了"SQL 等价判断"这一个任务**。Jev 官方声明 CJK 弱于英文，
   本次中文 SQL 场景表现良好，但不能据此外推到其他中文任务。
2. **业务链路里 Jev 只能替换"判断题"**：`generate_sql`、`correct_sql`、
   三路关键词扩展的产出都是文本，Jev 不生成文本，物理上无法替换；
   真正可能替换的是 `filter_table` / `filter_metric` 这类裁剪判断——**尚未验证**。
3. **已接入评测脚本**：`run_ragas_eval.py` 提供 `--judge {jev,ragas,both}`，**默认 `jev`**；
   `--judge ragas` 可切回原 DeepSeek 裁判，`--judge both` 两个都跑并输出一致率。
   判定逻辑统一放在 `eval/jev_judge.py`（含接口细节与口径说明），
   离线重判脚本 `eval/jev_equivalence_judge.py` 复用同一实现，避免两处漂移。
   第二轮产出的 `results_*.csv` 里的 `sql_equivalence` 仍是 ragas 口径，历史结果不受影响。

复现：

## 8. 遗留问题：精确率回落 0.213

第二轮执行准确率上去了，但**字段召回精确率从 0.736 掉到 0.523**，这个代价必须说清楚。

对比两轮的召回集合：

| 指标 | 第一轮（全句统一阈值） | 第二轮（按关键词独立阈值） |
|---|---|---|
| 平均召回字段数 | 5.21（1~9） | **7.97**（2~15） |
| 存在误召回的用例 | 44/63 | **60/63** |
| 误召回最多的字段 | `fact_order.date_id`（22 次） | **`fact_order.order_quantity`（42 次）** |
| 漏召回最多的字段 | `dim_date.year`（15 次）、`dim_date.month`（12 次） | 同左（基本没变） |

诊断很直接：按关键词独立算阈值，等于**每个关键词都保留自己的"第一名"**，
召回集合从 5.2 膨胀到 8.0 个字段。`order_quantity` 被误召回 42 次
（"销售""数量""销量""订单"这些词都会把它拉进来），而漏召回情况几乎没有改善
（`recall` 只从 0.826 涨到 0.844，涨 0.018）。

**换句话说：多放了 2.8 个字段/题的噪音，只换来 1.8 个百分点的召回率，不划算。**

漏召回的大头是 `dim_date.year`（15 次）和 `dim_date.month`（12 次），
说明时间维度字段的召回本身有系统性问题——这大概率是下一步该优先修的地方，
而不是继续在阈值上做微调。

### 建议的下一步（按优先级）

1. **改召回阈值策略**：折中方案——每个关键词的 Top-1 必留（保召回），
   其余字段仍按**全句相对阈值**过滤（保精确）。预期召回集合回到 5.5~6.5，
   召回率基本不掉，精确率回升到 0.65~0.70。
2. **单独修时间维度召回**：`dim_date.year/month` 漏召回 27 次，
   考虑在时间关键词上做定向召回（识别到时间语义就强制并入 `dim_date` 的粒度字段）。
3. **修「排除条件 + 汇总」语义**：在 `generate_sql` prompt 里补一条规则
   （问"是多少"且无分组维度时，即使带排除条件也要输出单个汇总值）。

## 10. 这次评测的几个方法论要点

1. **出题前先摸数据**。不知道真实取值范围，就会造出空结果题和无区分度题。
2. **用例入库前必须真跑一遍参考 SQL**。"看起来对"的 SQL 很可能查不到数据（耐克那条就是这么抓出来的）。
3. **主指标要确定性**。`execution_accuracy` 真正执行比对，不依赖 LLM 判断；
   只在"语义等价"这种必须靠理解的地方才用裁判 LLM，且要把判定口径写死在 prompt 里。
4. **分数掉了先分类**：是系统退化、是评测脚本有 bug、还是题目本身有歧义？
   这次 10 条失败里，只有 1 条是系统回归，1 条是脚本 bug，7 条是我出题的问题。
   不分类就动手改系统，会把评测集改歪来迁就系统。
5. **改一个指标要看另一个指标**。这次为了让召回更全，把精确率从 0.736 拉到了 0.523，
   召回率只涨了 0.018——必须拿数据算这笔账，不能凭"召回全一点总没错"的直觉。
6. **不是每个"用 LLM 的地方"都需要会写字的模型**。裁判环节换成只返回概率的 Jev 之后，
   F1 从 0.931 提到 0.984，63 条成本 $0.0034（7.3 节）。
   前提是先把判定口径拆成边界清楚的问题；而 SQL 生成、关键词扩展这类**产出是文本**的节点不能这么换。
7. **"拆得越细越稳"不是普适的**。7.3 节把等价判断拆成 6 个原子问题后，F1 反而比单点总体判断低 0.053——
   因为拆出来的子问题（"表与关联键是否一致"）和最终口径（"数据集合是否相同"）不同向。
   拆完之后要回头检查：每个子问题的"是"，是否都真的指向最终结论。
