> 修复对象：`NL2SQLAgent`

## 1. 一句话结论

定位并修复了**评测不可复现的根因**——不是模型幻觉，是 context 给了它错误的前提；
同时把评测集推翻重做（63 → 76 条，由脚本编译产出而非手写）。
重建后的评测集上 **执行准确率 100%（76/76）**，但**这个数字不能当成能力提升的证据**，
原因见第 5 节。

---

## 2. 根因修复：错误的前提，不是幻觉

### 2.1 症状

同一条问句「1月份的订单量是多少」连跑 5 次，生成 **4 个不同的 SQL**：
2 次正确（`WHERE d.month = 1`）、3 次错误（`WHERE d.year = 2026 AND d.month = 1`，返回 0 行）。

分阶段探测（关键词 → 召回字段 → 过滤表 → SQL）显示：**关键词抽取完全确定，不确定性集中在 `generate_sql`**。

### 2.2 根因

`add_extra_context` 把**系统当前日期**（2026-10-03）注入 `date_info`，而
`generate_sql.prompt` **没有任何规则**说明"用户没写年份时该怎么办"。

模型看到"现在是 2026 年"、用户问"1月份"，生成 `year = 2026` 是**完全合理的推断**——
它不是在幻觉，是在正确使用一份不完整的前提。数据实际只到 2025-12-31，所以必然查空。

### 2.3 修复

| 层 | 改动 |
|---|---|
| 仓库层 | 新增 `DWMySQLRepository.get_data_date_range()`，取事实表真实日期范围；转换逻辑抽成模块级纯函数 `format_business_date` 便于离线单测 |
| 状态层 | `DateInfoState` 增加 `data_range` 字段（该 TypedDict 只有 `add_extra_context` 一个构造点，影响面小） |
| 节点层 | `add_extra_context` 注入范围；**单独 try/except 降级**——取不到只记 WARNING，不能让整条问句失败 |
| Prompt | `generate_sql.prompt` 第 9 条：未显式写年份时严禁用 `date` 的年份补全；`correct_sql.prompt` 第 10 条同步 |

### 2.4 验收

修复后同一条问句连跑 5 次，**5/5 都生成不带年份的 `WHERE d.month = 1`**（修复前 2/5）。

> 注意：SQL 文本仍然每次不同，但只差在别名（`order_count` vs `订单量`、表别名 `o` vs `f`）。
> **语义已稳定，这足够支撑评测**——评测比对的是结果集，不是 SQL 字符串。

### 2.5 顺带修掉的三个真实缺陷

1. **过度分组**：问「各大区的销售额」生成 `GROUP BY r.region_id, r.region_name`，返回 31 行而非 7 行。
   根因是 `dim_region.region_id` 实际标识**省份**、`region_name` 才是**大区**，命名极具误导性。
   修复：prompt 加分组粒度规则 + `meta_config.yaml` 里把两个字段的 description 写明粒度
   （描述参与 embedding，改后**必须重建元知识库**）。
   **验收：本轮 6 条「各大区」题全部返回 7 行，确定性前置校验短路 0 次。**
2. **`correct_sql.py` 的 `input_variables` 只声明了 2 个**（模板占位符与实际传参都是 7 个）。
   该节点只在 SQL 校验失败时走到，长期未暴露。已加 AST 回归测试。
3. **`meta_config.yaml` 的 AOV 指向错误**：描述是"成交金额平均值"却指向 `order_quantity`，已改为 `order_amount`。

### 2.6 关于 `seed`：明确不加

DeepSeek 未文档化支持 `seed`，传了可能 400；且即便接受也只是 best-effort，
会给人"已确定性"的假象。确定性靠 `temperature=0`（已有）+ 修正错误前提，
**残余不确定性在评测报告里显式声明**。

## 3. 评测集重建（63 → 76 条）

旧集的两个硬伤：2 道题跨年后参考 SQL 语义已错、3 道含时间语义却没写年份。

### 3.1 出题方式也改了

**不再手写 jsonl**，改由 `eval/build_dataset.py` 编译产出：

- 题目写在源码的 `CASES` 列表里，**编译时每条真跑一遍**——参考 SQL 必须可执行、非空、
  且行数与声明的 `expected_rows` 一致，否则报错不产出文件。
  这一条当场抓出我最初写错的 2 条 HAVING 阈值。
- **`reference_columns` 由参考 SQL 自动推导**（约定 SQL 里每列都写 `别名.列名`）。
  手写标注正是 09 报告里"标注了系统召不回的字段"的来源。

### 3.2 题型矩阵

| 类别 | 条数 | 覆盖 |
|---|---|---|
| A 单指标聚合 | 8 | COUNT/SUM/AVG/COUNT DISTINCT、维表计数 |
| B 单级分组 | 11 | 大区(7行)/省(31)/品类(10)/品牌(61)/会员等级(4)/性别(2) |
| C 排序与 TopN | 9 | LIMIT N 与纯 ORDER BY 排名 |
| D 时间粒度与趋势 | 12 | 年/季/月/日、跨年对比 |
| E 时间×维度交叉 | 10 | 指定年季月 + 大区/品类/会员/品牌 |
| F 条件过滤 | 8 | 阈值、枚举值、HAVING、多条件交叉 |
| G 占比与排除 | 7 | 百分比、排除条件+汇总、条件聚合差值 |
| H 多表关联 | 5 | 三表 / 四表 JOIN |
| I 易错边界 | 6 | **2 条刻意不写年份，专门考"不许用当前年份"** |

### 3.3 入库校验

`python -m scripts.validate_dataset` 检查：结构完整、参考 SQL 只读且可执行非空、
`reference_columns` 真实存在于 `meta.column_info`、问句查重（含仅标点不同）、
含时间语义但未写年份（WARN）、声明的年份是否越界。无 FAIL 退出码 0。

> 这个脚本上线后**抓出了它自己的一个假阳性**：年份正则 `(?:19|20)\d{2}` 把
> 「超过**2000**的月份」里的阈值误判成年份。已改为**年份必须带"年"后缀**。

## 5. 关键发现

### 5.1 `dim_date.year` 的召回几乎是失效的（96.7% 漏召回）

| 字段 | 需要该字段的题数 | 漏召回次数 | 漏召回率 |
|---|---|---|---|
| `dim_date.year` | 30 | **29** | **96.7%** |
| `dim_date.month` | 16 | 13 | 81.2% |
| `fact_order.customer_id` | 17 | 7 | 41.2% |
| `fact_order.region_id` | 20 | 8 | 40.0% |
| `dim_product.product_id` | 25 | 4 | 16.0% |
| `fact_order.order_amount` | 35 | 0 | 0% |
| `dim_date.date_id` | 32 | 0 | 0% |

**`year` 基本永远召不回来，但系统仍然 100% 做对了时间类问句。**

原因是 `server/agent/time_utils.py` 里的规则补偿：识别到时间语义就问句，
`merge_retrieved_info` 会**强制并入时间维表的粒度字段**（日志里能看到"时间维度补全"）。

**这条架构依赖值得记一笔**：向量召回对时间维表字段（year/quarter/month）实际上是失效的，
系统靠一层确定性规则兜底。**只要这条规则被改动或误删，所有时间类问句会集体失效**，
而召回指标本身看不出来（`linking_recall` 0.835 看着还行）。

### 5.2 精确率 0.507：71/76 的题目存在误召回

召回集合平均放进了不少无关字段，但下游的 `filter_table` 节点把它们裁掉了。
这解释了为什么"召回质量平庸"与"执行准确率很高"能同时成立——
**裁剪节点在替召回兜底**，代价是更大的 prompt 与更高的延迟。

### 5.3 裁判的 1 条"假阴性"其实是风险信号，不是误判

「2024年和2025年的订单量分别是多少」：系统生成了 `WHERE d.year IN (2024, 2025)`，
参考 SQL 没有这个过滤条件（数据只有这两年，不加过滤结果一样），执行结果相同 → `correct`。
但 Jev 判**不等价**（概率 0.16），理由是 `same_filter` 不成立。

**Jev 是对的**——按"语义等价"口径，换一份含 2026 年数据的数据集，两条 SQL 结果就不同了。
这正是 10 号报告指出的口径差异：**裁判的反对票应作为"结果对但写法有隐患"的风险信号，
不能当误判丢掉**。

### 5.4 过度分组已修复

本轮的**确定性前置校验短路 0/76**，6 条「各大区」题全部返回 7 行。
修复前这类题的典型症状是返回 31 行。

## 6. 不能下的结论（诚实边界）

**「100%」不能当成能力提升的证据**，理由有三：

1. **评测集是新的，与历史结果不可比。** 63 条与 76 条不是同一把尺子，
   98.41% → 100% 这个对比在统计上没有意义。
2. **题目是我出的，天然偏向系统能答的。** 虽然入库前做了"答案唯一 + 参考 SQL 真跑"的校验，
   但没有做对抗性设计（比如刻意构造会让当前架构出错的题）。
3. **单次运行。** 已实测同一配置连跑两次会有 3~5 条翻转，单轮结果必须按噪声对待。

**而且 100% 是个天花板**：它意味着这套评测集已经无法区分"系统变好了"和"系统没变"。
下一轮如果要评估改进效果，**需要更难的题**，而不是在这 76 条上继续刷分。

## 7. 遗留问题与下一步

1. **召回层仍是最大短板**：精确率 0.507、`dim_date` 时间字段召回近乎失效。
   09 报告提过的折中方案（每关键词 Top-1 必留 + 其余走全句相对阈值）仍未验证。
2. **评测集需要加难度**：当前 100% 饱和。建议补一批对抗性题目
   （多轮对话、含糊指代、需要澄清的问句、超出数据范围的陷阱题）。
3. **评测 CSV 建议带上 `category` 列**：本轮分析是按 query 关联 `dataset.jsonl` 才切出类别维度的，
   加列后可以直接切片分析。
4. **裁判的两个口径仍未统一**：`execution_accuracy`（这份数据上对不对）与
   `jev_equivalence`（换份数据还对不对）。建议继续用 `--judge both` 互补，
   把 Jev 的反对票单独标记为"写法有隐患"。

## 9. 本轮的方法论要点

1. **先分清"模型错"和"前提错"。** 这次的不稳定根本不是模型幻觉，是我们喂了它一份
   不完整的前提（有当前日期、没有数据范围）。补上前提，5 次里 4 个不同 SQL 立刻收敛。
2. **把偶然的不稳定变成可测量的量。** 用"同问句连跑 N 次看 SQL 是否收敛"作为
   可执行的验收标准，而不是凭感觉说"稳定了"。
3. **出题过程要能自我纠错。** 参考 SQL 自动推导字段标注、编译期真跑比对行数，
   把 09 报告里靠人工复盘才能发现的问题变成机器能挡住的错误。
4. **给校验脚本也写测试。** 本轮校验脚本抓出了自己的年份识别假阳性——
   规则本身也会错，尤其是正则。
5. **基础设施的瞬时故障要重试，不要调大超时。** OpenRouter 首连偶发失败，
   单一把超时从 60s 调到更大只会每次白等更久；拆开连接/读取超时 + 退避重试才是对的。
6. **算漏召回要看比率不看次数。** `dim_date.year` 漏召回 29 次（旧集 15 次）看着变差，
   但分母从 16 题涨到 30 题——比率才是可比的。**换评测集后，绝对次数全部失去意义。**
